# FileHub 本机延迟排查记录（2026-09-21）

本轮只新增测试脚本和结果记录；项目原始 `epoll_handler.c` 未修改。

## 环境与方法

- 主机：wang，12 个逻辑 CPU，Linux 5.15.0-190-generic。
- 客户端与服务端都在同一台机器上，通过 127.0.0.1 通信。
- 使用 `filehub-test` 环境中的 wrk；每组运行 5 秒，重复 3 次，报告三轮中位数。
- 并发连接数为 1、10、50；1 连接使用 1 个 wrk 线程，其余使用 2 个线程。
- 测试对象：动态 `/status`、4 KiB `/index.html`、1 MiB `/large.bin`。
- 每个测试进程都使用临时文档根目录；三轮顺序由固定种子打乱。结果中无 socket 错误或非 2xx 响应。
- wrk 结果只代表本机回环环境，不是跨机器吞吐或生产容量数据。

复跑原始版本：

```sh
conda activate filehub-test
python tests/benchmark_latency.py --duration 5 --rounds 3
```

## TCP_NODELAY 临时对照构建

只在 `/tmp` 中复制源码并编译临时二进制。对照版本在 `epoll_handler.c` 中增加 `#include <netinet/tcp.h>`，并在 `accept4()` 成功后、把连接加入 epoll 前执行：

```c
int no_delay = 1;
if (setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &no_delay, sizeof(no_delay)) < 0) {
    perror("TCP_NODELAY");
    close(fd);
    continue;
}
```

其余源码、编译选项和测试参数保持一致。原始数据：[latency-20260921-112021](latency-20260921-112021)。

对照版本的 9 项 FileHub 集成测试全部通过。为排除机器状态变化，再次测原始构建：10 连接下 `/status` 为 221.02 req/s、p50 44.16 ms；4 KiB 文件为 221.53 req/s、p50 44.21 ms。复测原始数据：[latency-20260921-112216](latency-20260921-112216)。

另外保持原始服务端不变，仅在 Python 客户端收到响应头后设置 `TCP_QUICKACK`：20 次 4 KiB 请求的完整响应时间中位数从 44.167 ms 降至 0.521 ms；两组响应头时间分别为 0.625 ms 和 0.449 ms。该实验仍只使用本机回环网络，且不代表所有客户端都会设置 `TCP_QUICKACK`。

## 结论与边界

A-B-A 与客户端 `TCP_QUICKACK` 两个对照实验强烈支持：当前小响应约 44 ms 的固定等待来自 Nagle 与延迟 ACK 的交互。服务端开启 `TCP_NODELAY` 的单一变更可消除此现象。由于本账号没有回环网卡抓包权限，尚未用报文时序直接证明具体的 ACK 时间线。

这仍是临时对照实验，**并未将补丁合入项目正式源码**。若决定采用，应单独评估其他文件大小、CPU 占用、网络环境及长时间稳定性，并保留修改前后的同机结果。
